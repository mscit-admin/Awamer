# OWASP ASVS 5.0.0 — Verification Matrix (Level 3)

**Standard:** OWASP Application Security Verification Standard 5.0.0 (May 2025), all 345 requirements.
Source: the official `OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json` release file.
**Target level:** L3. Awamer is a remote-administration platform that holds a credential vault, a root VPN
helper, multi-tenant RBAC and live SSH/VNC/tunnel access, so ASVS treats it as a high-value application.
**Code assessed:** commit `35e84b6` (release 1.8.0, after the `production-closure/` phase).
**Assessment date:** 2026-10-23.
**Scope:** `backend/`, `desktop/` (web build and Tauri shell) and `deploy/` (nginx, compose, DB roles).

This matrix complements the existing awareness-level matrices (`OWASP_TOP10_MATRIX.md` and
`OWASP_API_SECURITY_MATRIX.md`). Those lists name risk categories. ASVS gives a pass/fail requirement for
each control.

## Method

- Each requirement was checked against the **current code**, not against earlier reports. Earlier documents
  in `security-final/` and `production-closure/` were used as leads and are cited where they hold evidence.
- Evidence means a file and line, a test ID, or a document. Unit suites for auth, JWT, crypto, config,
  logger, VPN and proxy trust were run and passed. Integration suites (`*.itest.ts`) are cited from
  `production-closure/FINAL_TEST_RESULTS.md` and were not re-run here, because they re-provision
  cluster-wide roles (OR-10).
- No repository code was changed by this assessment.

### Status values

| Status | Meaning |
|---|---|
| **PASS** | The control is present and evidenced (code, and a test where one exists). |
| **PARTIAL** | The control exists but is incomplete, or a known residual risk applies. |
| **FAIL** | The requirement is not met. The Gap column says what is missing. |
| **NO EVIDENCE** | The control may be met, but nothing shows it. Mostly ASVS documentation requirements with no matching document. |
| **N/A** | The requirement does not apply. Examples: no OAuth/OIDC (V10), no WebRTC (V17), no GraphQL. |

"Met" in the summaries means PASS ÷ (all − N/A). PARTIAL does not count as met.

### Documentation gaps (NO EVIDENCE)

Twenty requirements fail only because ASVS L3 asks for a written policy that does not exist yet. Adding these
documents to `security-final/` would close most of them:

- **Input validation rules and file-upload policy:** V2.1.1, V2.1.2, V5.1.1.
- **Authentication and session policy:** timeouts, concurrent sessions, contextual factors (V7.1.x, V8.1.3/4).
- **Cryptographic inventory, key-management policy and PQC migration plan:** V11.1.x.
- **Data classification and retention schedule:** V14.1.x, V14.2.7.
- **Logging inventory:** what is logged, where, retention (V16.1.1).
- **Dependency remediation SLA and dangerous-functionality register:** V15.1.x.

### Strong areas (PASS, confirmed)

- SQL is fully parameterised and every `spawn` uses argument arrays with no shell (V1.2.4, V1.2.5).
- JWT: HS256 is pinned and `none`/RS256/HS384/HS512 are rejected. `typ` is enforced per token type, and
  `exp`/`nbf` are checked (V9.x).
- Refresh rotation is atomic, with reuse detection that revokes the whole chain (V7.2.x).
- Every request and WebSocket frame re-checks live account state, role and `auth_version`. Password, MFA
  and role changes kill sessions, including live SSH (V7.4.x, V8.3.x).
- Grant and target privilege ceilings; tenant scoping in SQL (V8.2.x, V8.3.x).
- Argon2id, AES-256-GCM with 96-bit random IVs and full tags, and CSPRNG on the backend (V11.x).
- Login rate limiting and lockout that cannot be bypassed with `X-Forwarded-For` (restricted `TRUST_PROXY`,
  tests PROXY-TRUST-*) (V6.3.1, V2.4.1).
- Database least-privilege roles, no API docs in production, and production refuses to start on unsafe
  config (V13.x).
